## API keys

Every request authenticates with a key in the **`X-API-Key`** header:

```bash
curl -H "X-API-Key: cck_your_key_here" \
  "https://api.cctools.network/api/v1/public/status"
```

Keys are strings of the form `cck_` followed by 56 hex characters. There is no
`Authorization: Bearer` support. Sending a Bearer token returns `401`.

Create, list, and revoke keys at
[cctools.network/profile/api](https://cctools.network/profile/api). The
cleartext is shown exactly once at creation; afterward only the prefix is
visible.

How many active keys you can hold depends on your tier: **2 on Free**, and
**10 on Validator and Pro**. The rate limit is counted per key rather
than per account, so the cap is really a throughput cap, and the reviewed
tiers get the higher one because somebody vouched for the holder.

## Tiers

Your key inherits a tier from your account eligibility. The tier sets your
rate limit and is echoed on every response as `meta.tier`.

| Tier | Rate limit | Eligibility |
|---|---|---|
| **Free** | 60 req/min | A verified Human Score (connect a Canton wallet). Granted instantly, no review. |
| **Pro** | 600 req/min | Included with a [CCTools Pro](https://cctools.network/pro) subscription. Granted instantly, and runs for as long as the subscription does. |
| **Validator** | Unlimited | A Canton validator party ID. Auto-approved when the party is a known operator, otherwise reviewed. 12-month term, free. |

Free and Pro are self-service: open [/profile/api](https://cctools.network/profile/api)
and the button appears if you qualify. Validators submit a party ID on the same
page.

Building something that needs more than this? Apply on the same page and tell us
what you are building. Higher and custom limits exist; they are arranged per
account rather than picked from a list.

A Pro subscriber who renews can press the same button again to extend their API
access to match. Nothing is ever downgraded by pressing it: if you already hold
a validator or a negotiated tier, it stays.

## Rate limits

Limits are counted per key, per minute, **per connection**. The API runs as a
multi-process cluster where each process keeps its own counter, so a client
spreading requests across many connections can exceed the stated figure before
anything pushes back. Treat the number as the sustained rate to design for
rather than a ceiling to probe.

When you do exceed it you get `429` with a `Retry-After: 60` header:

```json
{ "error": "Rate limit exceeded", "code": "rate_limited" }
```

Every successful response also carries your ceiling in
`meta.rate_limit_remaining`, so you can back off before you hit the wall.

## Errors

| Status | `code` | Meaning |
|---|---|---|
| `400` | `bad_request` | Malformed parameter. |
| `401` | `unauthorized` | Missing, malformed, revoked, or expired key. |
| `404` | `not_found` | No such resource (e.g. unknown slug). |
| `429` | `rate_limited` | Over your per-minute limit. Retry after the header. |
| `503` | `warming_up` | A cron-warmed dataset has a cold cache. Retry in a minute; this is not an empty result. |

All errors share the shape `{ "error": "...", "code": "..." }`.

## Good practice

<AccordionGroup>
  <Accordion title="Keep keys server-side" icon="server">
    Never ship a key in a browser bundle or mobile app. Proxy through a backend
    you control. A leaked key can be used up to its rate limit until you revoke it.
  </Accordion>
  <Accordion title="Rotate on suspicion" icon="rotate">
    Revoking is immediate: the key starts returning `401` right away. Mint a
    replacement first, cut over, then revoke the old one.
  </Accordion>
  <Accordion title="Handle 429 gracefully" icon="clock">
    Respect `Retry-After`. For steady workloads, stay under your tier ceiling
    rather than bursting and backing off.
  </Accordion>
</AccordionGroup>
