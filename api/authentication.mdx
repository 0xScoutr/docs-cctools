## API keys

Every request authenticates with a key in the **`X-API-Key`** header:

```bash
curl -H "X-API-Key: cck_your_key_here" \
  "https://api.cctools.network/api/v1/public/status"
```

Keys are strings of the form `cck_` followed by 56 hex characters. There is no
`Authorization: Bearer` support. From a browser a Bearer token returns `401`.
From a command-line client such as curl or python-requests it is rejected one
layer earlier, as `403 {"error":"Forbidden"}` with no `code` field, because a
request carrying no `X-API-Key` is not recognised as an API client at all.
Always send `X-API-Key`.

Create, list, and revoke keys at
[cctools.network/profile/api](https://cctools.network/profile/api). The
cleartext is shown exactly once at creation; afterward only the prefix is
visible. Once you hold one,
[cctools.network/api-docs](https://cctools.network/api-docs) runs any endpoint
against it in the browser.

How many active keys you can hold depends on your tier: **2 on Free**, and
**10 on Validator and Pro**. The rate limit is counted per key rather
than per account, so the cap is really a throughput cap, and the reviewed
tiers get the higher one because somebody vouched for the holder.

## Tiers

Your key inherits a tier from your account eligibility. The tier sets your
rate limit and is echoed on every response as `meta.tier`.

| Tier | Rate limit | Eligibility |
|---|---|---|
| **Free** | 60 req/min | A verified Human Score (connect a Canton wallet). Granted instantly, no review. |
| **Pro** | 600 req/min | Included with a [CCTools Pro](https://cctools.network/pro) subscription. Granted instantly, and runs for as long as the subscription does. |
| **Validator** | No per-key limit | A Canton validator party ID. Every submission is reviewed by a person, usually within one business day. 12-month term, free. |

<Warning>
No per-key limit is not the same as no limit. Every request to `/api/`, on
every tier including Validator, also counts against a ceiling of **600
requests per minute per IP address**. Sustained breaches escalate to a
temporary block on the IP, so back off on a `429` rather than retrying at
once. Planning a backfill that needs more than that? Ask us first.
</Warning>

Free and Pro are self-service: open [/profile/api](https://cctools.network/profile/api)
and the button appears if you qualify. Validators submit a party ID on the same
page.

**Eligibility is checked when a key is issued, never on the requests you make
with it.** A verified Human Score is what unlocks the self-service button; it is
not re-tested per call. Keys we issue directly to an organisation are attached to
that organisation rather than to a person, so there is no account to verify and
nothing for a server-to-server integration to keep alive. A key stops working for
exactly three reasons: it is revoked, it expires, or it is called outside its
scopes.

Building something that needs more than this? Apply on the same page and tell us
what you are building. Higher and custom limits exist; they are arranged per
account rather than picked from a list.

A Pro subscriber who renews can press the same button again to extend their API
access to match. Nothing is ever downgraded by pressing it: if you already hold
a validator or a negotiated tier, it stays.

## Rate limits

Limits are counted per key, per endpoint, per minute, **per process**. The API runs as a
multi-process cluster where each process keeps its own counter, so a client
spreading requests across many connections can exceed the stated figure before
anything pushes back. Treat the number as the sustained rate to design for
rather than a ceiling to probe.

When you do exceed it you get `429` with a `Retry-After: 60` header:

```json
{ "error": "Rate limit exceeded", "code": "rate_limited" }
```

Every successful response also carries your ceiling in
`meta.rate_limit_remaining`. On tiers with no per-key limit it is `null`, so
type it as nullable.

<Warning>
Despite the name, `rate_limit_remaining` is your **ceiling**, not a countdown.
It returns the same number on every response and never decrements, because an
exact per-request count would cost a database read on the hot path. Do not
branch on it dropping toward zero, since it never will. Use the `429` and its
`Retry-After` header as your real backoff signal.
</Warning>

## Errors

| Status | `code` | Meaning |
|---|---|---|
| `400` | endpoint-specific | Malformed parameter, e.g. `invalid_slug`, `invalid_window`, `invalid_party_id`. |
| `401` | `unauthorized` | Missing, malformed, revoked, or expired key. |
| `403` | `forbidden` | The resource exists but is not public, e.g. a private profile. |
| `404` | endpoint-specific | No such resource, e.g. `project_not_found`, `post_not_found`. |
| `422` | `unsupported_token` | The project has no token to report on. |
| `429` | `rate_limited` | Over your per-minute limit. Retry after the header. |
| `500` | `internal` / `query_failed` | Our fault. Safe to retry. |
| `502` | `upstream_unavailable` | A market data source we depend on is down. |
| `503` | `warming_up` | A cron-warmed dataset has a cold cache. Retry in a minute; this is not an empty result. |

Most errors carry `{ "error": "...", "code": "..." }`, but the `code` is
specific to the endpoint rather than drawn from a fixed list. **Branch on the
HTTP status, which is stable, and treat `code` as detail.** Two responses come
from the edge layer before the handler runs and carry only `{ "error" }` with
no `code` at all: the `403` for a keyless tool client, and the `429` for the
per-IP ceiling.

## Good practice

<AccordionGroup>
  <Accordion title="Keep keys server-side" icon="server">
    Never ship a key in a browser bundle or mobile app. Proxy through a backend
    you control. A leaked key can be used up to its rate limit until you revoke it.
  </Accordion>
  <Accordion title="Rotate on suspicion" icon="rotate">
    Revoking is immediate: the key starts returning `401` right away. Mint a
    replacement first, cut over, then revoke the old one.
  </Accordion>
  <Accordion title="Handle 429 gracefully" icon="clock">
    Respect `Retry-After`. For steady workloads, stay under your tier ceiling
    rather than bursting and backing off.
  </Accordion>
</AccordionGroup>
